# Feature: Payments

## Purpose
Gate course enrollment behind a payment, supporting both an online
gateway and manual (cash/transfer) confirmation.

## Methods

| Method | Type | Flow |
|---|---|---|
| `card` | Online | Student redirected to/embeds a payment gateway (e.g. Paymob, which covers both card and Fawry in Egypt) checkout; server creates a `pending` payment first, gateway webhook flips it to `succeeded`, which triggers enrollment. |
| `fawry` | Online | Same gateway integration as `card` — Fawry reference/cash-in code generated by the gateway; webhook-driven like `card`. |
| `vodafone_cash` | Manual | Student submits a `pending` payment with a `referenceNote` (transaction id/phone used). Teacher or Admin reviews and marks `confirmed`/`rejected`. |
| `bank_transfer` | Manual | Same manual review flow as `vodafone_cash`. |

> Which online gateway to integrate (Paymob is the common choice for
> Egypt-based card + Fawry support) needs to be confirmed before
> implementation — track the decision in a new ADR once chosen.

## User stories
- As a student, I choose a payment method when enrolling in a paid
  course, and see my payment's status (pending/succeeded/confirmed/rejected).
- As a teacher, I see a list of `pending` manual payments for my own
  courses and can confirm or reject each one.
- As an Admin, I see all payments across all teachers, and can also
  confirm/reject manual payments on any teacher's behalf.
- As a teacher creating a student directly (see `features/students.md`),
  the resulting payment is auto-`confirmed` (no online step) so
  enrollment happens immediately.

## Data
`payments/{paymentId}` — see `database/collections.md`. Enrollment
creation is a side effect of a payment reaching `succeeded`/`confirmed`,
handled server-side in the payment service — never created directly by
a client request to the `enrollments` endpoint.

## Authorization
A student can create their own `pending` payment and read their own
payment history (never anyone else's). Only the owning teacher or Admin
can confirm/reject a manual payment; only the server-side gateway
webhook handler can set `succeeded`.

## Security notes
- The gateway webhook endpoint must verify the provider's signature
  before trusting any payload (per `security/README.md`'s general
  external-input rules).
- Amounts are always taken from the course's stored `price` server-side
  — never trusted from client-submitted payment amounts.
