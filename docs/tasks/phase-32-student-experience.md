## TASK-3201: Student profile — age, current stage, name, photo
- Description: Add a simple student-facing profile: editable `displayName` (already exists on `users`), `avatarUrl` (Cloudinary, optional — add to `users` schema if not already present for students), and a derived/display `age` field. Age: rather than storing a raw age that goes stale, store `birthDate` (optional date) and compute age server-side for display — flagged here as Claude's suggestion over a raw `age` number, open for the user to override if a raw number is preferred. `stageId` already exists on `users` for students (Phase 10) and is shown read-only here (changing grade level is an Admin action, not self-service, to keep enrollment/subscription data consistent).
- Goal: A student has a lightweight profile of their own, not just an account record.
- Dependencies: Phase 10 (`users.stageId` for students)
- Affected modules: `lib/validation/user.schema.ts` (or student-specific profile schema), `lib/server/repositories/userRepository.ts`, `app/api/student/profile/route.ts` (new), `app/[locale]/(protected)/student/profile/page.tsx` (new), `components/student/*`
- Acceptance criteria: student can view/edit `displayName`, `avatarUrl`, `birthDate`; `stageId` shown but not editable by the student.
- Testing requirements: API route tests for get/update including the read-only `stageId` enforcement; schema tests for `birthDate` validation.
- Documentation requirements: `docs/database/collections.md` `users` table gets `birthDate`/`avatarUrl` rows if not already present.
- Status: Done — self-service profile sits directly on the existing `users` doc rather than a new collection (unlike the teacher's `teacherProfiles`), since it's just `displayName` (already existed) plus one new field `birthDate`. New `lib/validation/user.schema.ts` (`updateStudentOwnProfileSchema`, `computeAgeFromBirthDate`) validates `birthDate` as an ISO `YYYY-MM-DD` string bounded to a plausible student age (2–25, matching `account.schema.ts`'s existing `ageField` range) and never in the future. `userRepository.ts` gained the `birthDate` field on `UserDoc` and reuses its existing `updateProfile(uid, fields)` method (already used by the Admin edit flow) for the self-service patch rather than adding a duplicate write method. New `studentProfileService.getMyProfile`/`updateMyProfile` (role-gated to `student`, session's own `uid` always) computes `age` from `birthDate` at read time — never stored, so it can't go stale, per this task's own suggestion — and joins `stageId` to its `educationStages` display name for the read-only grade-level field. New `GET`/`PATCH /api/student/profile` and `student/profile/page.tsx` + `StudentProfileForm`. Avatar upload is deliberately *not* duplicated here: the form reuses TASK-1005's existing signed-upload flow and `PATCH /api/student/settings/avatar` (same Cloudinary field as the account-settings picture) rather than adding a second avatar endpoint. `stageId` is never accepted in this route's body — read-only, an Admin-only change via Student management, to keep enrollment/subscription data consistent. Also updated `DashboardTopbar`'s profile-icon routing (TASK-3103's teacher precedent) so a student session now goes to `/student/profile` too, instead of `/student/settings`. New translations under `studentDashboard.myProfile` in both `messages/en.json`/`messages/ar.json`. Documentation: `docs/database/collections.md`'s `users` table gets a `birthDate` row; `docs/features/students.md` gets a new "Student self-service 'My Profile'" section. Full verification run for real this session (network available): `npm install`, `npx vitest run` (111 files / 745 tests passing, up from 719 — new tests for `computeAgeFromBirthDate`, `updateStudentOwnProfileSchema`, `studentProfileService`, and the new route), `npx eslint` (0 errors, same 5 pre-existing unrelated warnings), `check-translations`/`check-rtl`/`check-contrast` all pass, `npx next build` compiles successfully. `npx tsc --noEmit` has the same two pre-existing, unrelated failures noted in prior sessions (`meeting-notifications.tsx`/`class-reminder-banner.tsx`) — neither touches anything this task changed. Phase 32 stays `In Progress`: TASK-3203 (rename "My Teachers" → "Teachers") is next — its dependencies (TASK-2301, TASK-2302, TASK-3101, Phase 29) are all satisfied.

## TASK-3204: Course detail view from a teacher's account page — access-gated content

Non-eligible students see the course structure (lesson titles/count) but a locked state on gated lessons.
- Dependencies: TASK-2303 (existing "teacher courses view, scoped to enrollment" — this task extends it to the general/non-enrolled case), TASK-3105

- Documentation requirements: `docs/features/lessons.md`, `docs/features/enrollment.md`.
- Status: Done — `assertStudentHasCourseAccess` (new guard in `lib/auth/guards.ts`) is the shared access rule: an admin, or a student with a non-cancelled enrollment in the course, or a student with an active Phase 29 subscription covering the course's `teacherId`+`subjectId`+`stageId` (`courseService.hasActiveSubscriptionForCourse`, new — a subscription is the teacher+subject+stage relationship, so it applies to every course in that subject/stage, not just one; see `subscriptionRepository`'s own doc comment). `lessonService.getLessonForStudent` now checks this (enrollment OR subscription) instead of enrollment alone, so a directly-requested gated lesson is rejected server-side regardless of subscription status — satisfying the "API-level, not just UI" acceptance criterion. New page `student/courses/[courseId]/page.tsx` (open to any authenticated student, no enrollment/subscription required to view metadata) shows title/description/price/enrolled-or-subscribed badge and the lesson list — locked lessons render without a link, unlocked ones link to the existing `student/courses/[courseId]/lessons/[lessonId]` player, whose own `getLessonForStudent` gate is the real enforcement (checked independently, not derived from what this page rendered). ## TASK-3205: Student weekly schedule page
- Description: A dedicated page listing every one of the student's classes across the week (derived from the `schedule` docs of every teacher the student is subscribed to), laid out as a clean weekly timetable (days as columns or rows, time slots), matching the app's existing design system/tokens rather than a generic table.
- Dependencies: Phase 6 (`schedule` collection), Phase 29 (subscriptions determine which slots are "the student's")
- Affected modules: `app/api/student/schedule/route.ts` (new), `app/[locale]/(protected)/student/schedule/page.tsx` (new), `components/student/*`
- Acceptance criteria: shows every schedule slot for every teacher the student is subscribed to, grouped/sorted by day and time; visually consistent with `docs/design-system`.
- Testing requirements: API test scoping slots to the caller's subscriptions; a visual/consistency check against the design-system doc (manual or snapshot).
- Documentation requirements: `docs/features/schedule.md` (new or extend existing).
- Status: Done — new `scheduleRepository.listByTeacherIds` (chunked `in` query on `teacherId`, same pattern as `teacherProfileRepository.findByIds`) is the schedule-side half; `studentScheduleService.listMySchedule` is the service-layer scoping (this task's own acceptance criterion, not just an API test): it derives the caller's `active`-subscription teacherIds from `subscriptionRepository.listByStudent` (Phase 29 "subscribed" — same definition `teacherDirectoryService` already uses, not `enrollments`), short-circuits to `[]` without querying schedule when there are none, then joins each slot to the teacher's `displayName` (`teacherProfileRepository.findByIds`) and the subject's localized `name` (`subjectRepository.list`) so the page needs no client-side lookups. `GET /api/student/schedule` exposes it (mirrors `GET /api/student/teachers`'s shape). New page `student/schedule/page.tsx` is a read-only server component (no client state needed, unlike the teacher's `schedule-manager.tsx`) rendering a 7-column day grid, each day's slots as `Card`s showing time/duration/subject/teacher/optional note, using only semantic tokens (`Card`, `Badge`, `text-foreground`, etc.) per `docs/design-system`; empty state uses the shared `EmptyState` primitive. New "Schedule" entry added to `StudentSidebar`'s nav (between "Teachers" and "Settings"). New translations under `studentSchedule` plus `studentDashboard.nav.schedule` in both `messages/en.json`/`messages/ar.json` — parity verified by running `npm run check-translations` (1000 keys in sync; `node_modules` installed successfully this session, unlike TASK-3203/3204's sandbox).
