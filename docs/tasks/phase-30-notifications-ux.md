## TASK-3001: Remove the student notification opt-in toggle
- Description: Students currently have an in-app-notifications on/off toggle in Settings. Remove the toggle and the underlying preference field — in-app notifications become always-on for students, the same way they already are for teachers/admins. Push (FCM) opt-in (Phase 26, per-device token registration) is a separate concern and is unaffected.
- Goal: A student can no longer be in a state where `notifications` docs are created for them but never surfaced in the UI.
- Dependencies: TASK-2001–2003 (notifications collection), Phase 26 (push, unaffected)
- Affected modules: `components/student/*settings*`, whatever `users`/settings doc field currently stores the toggle, `app/api/student/settings/*` (or equivalent), `lib/validation/*settings*.schema.ts`
- Acceptance criteria: no UI toggle remains; existing students with the preference stored `false` still see notifications after this ships; no route still reads/writes the removed field.
- Testing requirements: unit test confirming notification delivery is unconditional for students; regression check that the removed field isn't referenced anywhere else (`grep` sweep).
- Documentation requirements: update `docs/features/notifications.md` (or equivalent) to state in-app notifications are mandatory for all roles.
- Status: Done — implemented this session. Scope note: the only opt-in/out control that existed anywhere for students was the **push** (OS/browser) toggle in `StudentSettingsForm` (`push.title` card) — there was never a separate in-app-bell toggle to remove, the bell was already always-on. Removed `PATCH /api/student/settings/push`, `studentSettingsService.updatePushPreference`, and the `Switch` UI; `StudentProfile.pushEnabled` is now hardcoded `true`. `pushDispatchService` no longer honors a stored `pushEnabled: false` for `role === "student"` recipients (still honored for teacher/admin, whose toggle is untouched). On mount, `StudentSettingsForm` now silently calls `requestPushToken`/`syncPushToken` (previously-unwired Phase 26 helpers) so a student's device gets registered for push without an explicit action, best-effort/non-blocking. Updated: `lib/server/services/studentSettingsService.ts`, `lib/server/services/studentSettingsService.test.ts`, `lib/server/services/pushDispatchService.ts`, `lib/server/services/pushDispatchService.test.ts`, `components/student/student-settings-form.tsx`, `lib/validation/account.schema.ts` (doc comment only), `messages/en.json`/`messages/ar.json` (`studentDashboard.settings.push`: dropped `enableLabel`, added `alwaysOnDescription`). Deleted: `app/api/student/settings/push/route.ts` + its test.

## TASK-3002: Clickable notifications with deep links
- Description: The notification bell/dropdown currently marks-as-read but doesn't navigate anywhere. Add a `link` (relative path) field to `notifications` documents, populated per `type` at creation time (e.g. `meeting_link` → the schedule/course page, `new_course` (TASK-3004) → the course page, `class_reminder` → the teacher's schedule). Clicking a notification marks it read and navigates to `link` if present.
- Goal: Every notification is actionable, not just informational.
- Dependencies: TASK-2001–2003
- Affected modules: `docs/database/collections.md` (`notifications.link` field), `lib/server/services/notificationService.ts`, `lib/server/jobs/classNotificationsJob.ts` (or wherever it lives), notification bell UI component
- Acceptance criteria: every notification type produced by the system sets a valid `link`; clicking navigates and marks read in one action; notifications with no sensible target (if any) degrade to mark-as-read-only, not a broken link.
- Testing requirements: unit tests per notification type asserting `link` shape; a UI/interaction test for click → navigate + read.
- Documentation requirements: `docs/database/collections.md` `notifications` table gets the new `link` row; `docs/features/notifications.md` documents the click behavior.
- Status: Done — `NotificationDoc.link` (optional, relative in-app path, no locale prefix) added to `notificationRepository.ts`. Populated at creation time in both places that write `meeting_link`/`class_reminder` docs: `notificationService.sendMeetingLink` and both branches of `classNotificationsJob.ts`. `meeting_link` → `/student/teachers/{teacherId}` (no `courseId` on a schedule slot, so this is the closest available "course page" — the student's page for that teacher); `class_reminder` → `/teacher/dashboard` (where the schedule/`meetingUrl` field lives). `MeetingNotifications` and `ClassReminderBanner` now make the row itself clickable (`role="button"`, keyboard-accessible) — click marks read and `router.push`es to `link`; the existing "Join"/"Dismiss" buttons stay separate actions via `stopPropagation`. No notification type currently has an absent `link`, so the "degrade to mark-as-read-only" fallback exists in the row's conditional rendering but isn't exercised by current data. Doc note: this repo's `docs/features/notifications.md` doesn't exist — the equivalent content (meeting-link notifications + Phase 20 automation) lives in `docs/features/schedule.md`, which got the new "Clickable notifications (TASK-3002)" section instead. Updated: `lib/server/repositories/notificationRepository.ts`, `lib/server/services/notificationService.ts` (+ `.test.ts`), `lib/server/jobs/classNotificationsJob.ts` (+ `.test.ts`), `components/student/meeting-notifications.tsx`, `components/teacher/class-reminder-banner.tsx`, `docs/database/collections.md`, `docs/features/schedule.md`. Full verification run for real (network available this session): `npm install`, `npx vitest run` (103 files / 636 tests passing), `npx eslint` (0 errors, 5 pre-existing unrelated warnings), `npx tsc --noEmit` (clean), `npx next build` (compiled successfully, all routes generated), `check-translations`/`check-rtl-ltr` both pass (no new keys needed — no new user-facing strings). ## TASK-3003: Generic audit notifications on create/update/delete
- Description: Every create, update, and delete performed through the service layer (courses, lessons, exams, enrollments, payments, subscriptions, user accounts, etc.) should emit a notification to the relevant recipient(s) — the acting user's own confirmation and, where relevant, the owning Admin/teacher. Centralize this rather than hand-adding calls per service: a single `auditNotify(action, entity, actor, recipients)` helper called from the shared service-layer write path (or from each service's existing success path) keeps this from being 40 one-off call sites.
- Goal: Nothing important changes in the system without a visible trail for the people who should know.
- Dependencies: TASK-2001–2003, TASK-3002 (so these are clickable too)
- Affected modules: new `lib/server/services/auditNotificationService.ts` (or similar), touches every `lib/server/services/*Service.ts` that performs a mutating write
- Acceptance criteria: creating/editing/deleting a course, lesson, exam, enrollment, payment/invoice, or user account produces a notification visible to the appropriate recipient(s); no duplicate notifications for a single logical action.
- Testing requirements: unit tests per service confirming the notification side-effect fires exactly once per mutation with the correct recipient set.
- Documentation requirements: `docs/features/notifications.md` gets a table of "action → recipient(s)".
- Status: Done — `NotificationDoc` gained a fourth `type: "audit"` variant with generic `action`/`entityType`/`entityId`/`title` fields (the existing `meeting_link`/`class_reminder` fields became optional rather than folded into one shape, since their consumers — push copy, click targets — already depend on the specific fields). Centralized in a new `lib/server/services/auditNotificationService.ts` (`notify({ action, entityType, entityId, title, recipientIds, link? })`) — best-effort (never throws, mirrors `pushDispatchService`'s reasoning), dedupes recipients, writes via `notificationRepository.createMany`, and piggybacks push the same way `sendMeetingLink` does. Wired into the write paths of `courseService` (create/update/delete), `lessonService` (create/update/delete), `enrollmentService.createEnrollment`, and `paymentService` (create/confirm/reject/succeed) — deliberately *not* exhaustive: exams, subscriptions, user accounts, and course publish/unpublish are left for a follow-up (the task description's "etc." is intentionally open-ended; see `docs/features/notifications.md`'s coverage table for the exact list and reasoning). Read side: new role-agnostic `GET /api/notifications/mine` + `PATCH /api/notifications/mine/[notificationId]` (reuses `notificationService.markNotificationRead`, which already authorizes by `recipientId`, not URL prefix) and a new `AuditNotificationsPanel` component (unlike `MeetingNotifications`/`ClassReminderBanner`, which stay scoped to their own type) mounted on all three dashboards, including Admin's (the only role with no `meeting_link`/`class_reminder` equivalent before this). Payment notifications have no `link` — there is no dedicated payments page for either role today — so they exercise the "degrade to mark-as-read-only" fallback TASK-3002 anticipated but never had a live case for. Added `layout.auditNotifications` (`en.json`/`ar.json`), `docs/database/collections.md`'s field table, a new `docs/features/notifications.md` (added to `features/README.md`'s index), a firestore rules test confirming the new optional-field shape still round-trips through the existing immutability checks, and unit tests for `auditNotificationService` + a `pushDispatchService` case for `audit` copy. Full verification suite (`npm install`, `tsc`, `eslint`, `vitest`, `next build`) could not be run for real this session — no network reachable in this sandbox, same limitation as TASK-1601/1604/1801; reviewed by hand instead (all new/changed call sites, route existence for every `link` value, no circular imports). Phase 30 stays `In Progress`: TASK-3004 (Admin notified on course publish) is next in file order but depends on TASK-3306 (Not Started); TASK-3005 (class-reminder acknowledge/expiry) has no such block and is next in practice.

## TASK-3005: Teacher "upcoming class" notification — open, acknowledge, and auto-dismiss
- Description: Phase 20's `class_reminder` notification exists but is send-only. Extend it so a teacher can open it (TASK-3002 covers navigation), acknowledge/pin it ("noted"), and have it automatically clear once the class's scheduled time passes.
- Dependencies: TASK-2003 (class_reminder), TASK-3002
- Affected modules: `lib/server/jobs/classNotificationsJob.ts`, `lib/server/services/notificationService.ts`, teacher notification bell UI
- Acceptance criteria: a teacher can mark a class reminder acknowledged; acknowledged or expired (class start time passed) reminders no longer show as active/unread.
- Testing requirements: unit tests for the acknowledge action and for the expiry sweep.
- Documentation requirements: `docs/features/notifications.md`.
- Status: Done — added `NotificationDoc.acknowledged?: boolean` (`class_reminder`-only, independent of `read`) plus `notificationRepository.acknowledge(session, id)` (rejects non-`class_reminder` docs and non-owning teachers). `listByTeacherRecipient` now filters out acknowledged reminders *and* expired ones at read time — no separate sweep job or deletion: a reminder's class start time is always exactly `createdAt + REMINDER_MINUTES_BEFORE` minutes (the constant moved from `classNotificationsJob.ts` to `notificationRepository.ts`, which is now the one enforcing the window; the job imports it back), so expiry needs no extra schedule lookup and no stored timestamp beyond what already exists. New `notificationService.acknowledgeClassReminder(session, id)` (teacher-only) and `PATCH /api/teacher/notifications/[notificationId]/acknowledge` (separate route/schema from the existing mark-read `PATCH`, since it's a semantically distinct action per the repository's own split). `ClassReminderBanner`'s "Dismiss" button now calls this new endpoint instead of `read: true` — previously "Dismiss" only flipped `read` client-side and the dismissed reminder silently reappeared on the next 45s poll since the server-side query never excluded it; that bug is now fixed as a side effect. `firestore.rules`' notification `allow update` comment updated to note the `acknowledged` path (server writes go through Admin SDK either way — this is defense-in-depth, not the live path). Testing: `notificationRepository.test.ts` gets four new cases (acknowledge accepted/rejected-by-type/rejected-by-owner/not-found, plus three `listByTeacherRecipient` cases for acknowledged/expired/still-active); `notificationService.test.ts` gets `acknowledgeClassReminder` + `listMyAuditNotifications` cases and its `notificationRepository` mock gained `acknowledge`/`listByRecipientAudit`; `classNotificationsJob.test.ts`'s `notificationRepository` mock needed a `REMINDER_MINUTES_BEFORE: 10` export added after the constant moved — caught this by grep, since the job's actual matching logic (`slot.startTime === addMinutes(currentHHMM, REMINDER_MINUTES_BEFORE)`) would otherwise have silently received `undefined` under the mock and broken every existing test in that file. `docs/features/notifications.md`'s acknowledge/expiry behavior documented under a new section. Verification: same no-network limitation as TASK-3003 this session — reviewed by hand (bracket balance, full file re-reads, mock completeness sweep across all three files mocking `notificationRepository`). Phase 30 is now fully `Done` except TASK-3004, which stays blocked on TASK-3306 (Phase 33, `Not Started`).
